# 도구 권한: Ask, Auto, Yolo

데스크톱 컴포저 아래의 Ask/Auto/Yolo 컨트롤은 Patty Code가 도구 권한 승인을 처리하는 방식을 설정합니다. 세 모드 모두 계속 표시되므로 단축키나 설정 페이지에 의존하지 않고 바로 전환할 수 있습니다.

도구 권한은 협업 모드와 독립적입니다:

- **협업/런타임 모드**는 Patty Code가 작업을 어떻게 진행하는지 결정합니다(가벼움(lightweight), 균형(balanced), 또는 전달 우선(delivery-first)).
- **도구 권한**은 통제된 도구가 실행 전에 승인을 기다릴지 여부를 결정합니다.

## 빠른 비교

| 모드 | 동작 | 적합한 경우 | 부적합한 경우 |
| --- | --- | --- | --- |
| Ask | 통제된 도구(쓰기, 명령 등) 실행 전에 승인을 요청합니다. | 익숙하지 않은 리포지토리, 고위험 편집, 프로덕션 관련 작업, 단계별 검토. | 위험도가 낮은 반복 작업이 많거나 이미 연속 실행을 신뢰하는 경우. |
| Auto | 일반 도구 권한을 자동 승인하며, 명시적 `ask`/`deny` 규칙과 플랜 확인은 여전히 적용됩니다. 범위가 한정된(bounded) 새 프로젝트/참조 메모리는 안전한 생성 전용(create-only) 경로를 사용할 수 있으며, 다른 메모리 변경은 여전히 질문합니다. | 일상적인 코드 읽기, 소규모 수정, 테스트, 신뢰하는 워크스페이스에서의 일반 구현. | 모든 쓰기나 명령을 수동으로 확인하고 싶은 경우. |
| Yolo | 일반 도구 권한 프롬프트를 건너뛰어 쓰기와 명령이 더 적은 중단으로 실행되도록 합니다. `deny` 규칙, 플랜 확인, 질문하기, 강제된 새 승인은 여전히 적용됩니다. | 임시 브랜치, 롤백 가능한 워크트리(worktree), 확인된 플랜 이후의 대량 기계적 편집. | 프로덕션, 민감한 파일, 삭제/게시/푸시, 또는 불분명한 요구 사항. |

## Ask 모드

Ask는 가장 보수적인 도구 권한 모드입니다. Patty Code가 도구 호출에 대해 승인이 필요하면 승인 카드가 나타나며, 한 번 허용(Allow once), 세션 동안 허용(Allow for the session), 항상 허용(Always allow), 또는 거부(Deny)를 선택할 수 있습니다.

Dynamic Bash는 더 넓은 Bash, 접두사(prefix), 또는 glob 규칙을 절대 상속하지 않습니다. 매개변수/산술 확장, 할당, 리다이렉트, 히어독(heredoc), glob은 여전히 일반 모드 폴백을 따르지만, 중첩/간접 실행은 대화형 Ask 및 Auto에서 이 인간 승인 경로를 요구합니다. 재사용 가능한 선택은 동일한 완전한 명령을 `Bash=<literal>`로 저장합니다.

### 승인 카드 단축키

- `←`/`→`는 강조 표시된 액션을 순환합니다.
- `Enter`는 강조 표시된 일반 도구 승인 액션을 확인하며, 기본값은 "한 번 허용(Allow once)"입니다.
- `1`/`2`/`3`/`4`는 해당 번호의 일반 도구 승인 액션을 선택합니다.
- 플랜 확인에는 **실행 시작(Start execution)** / **플랜 수정(Revise plan)** / **실행하지 않고 종료(Exit without executing)**의 세 가지 직접 액션이 있습니다. Desktop에서는 한 번의 클릭 또는 해당 숫자 키를 사용하세요. CLI에서는 해당 숫자 키를 사용하거나 행을 선택한 후 `Enter`를 누르세요. `n`/`Esc`는 호환성을 위해 플랜 작성 상태를 유지합니다. 종료는 대기 중인 플랜을 거부하고 실행 턴을 시작하지 않은 채 Normal로 돌아갑니다.
- CLI 플랜 확인이 대기 중이 아닐 때 `Esc`는 현재 작업을 중지합니다.
- `Tab`으로 버튼에 이동한 후 `Enter`를 누르면 해당 포커스 버튼이 실행됩니다(강조 표시에 의해 무시되지 않습니다).

헤드리스 `patcode run`에는 응답할 승인 카드가 없습니다. 따라서 기본 Ask 자세는 프롬프트를 추가하거나 조용히 승인하는 대신 작성자 폴백(writer fallback)과 명시적 ask 규칙에 대해 기본 거부(fail closed)로 동작합니다. 무인 자동화에서 일반 작성자 폴백을 허용해야 한다면 기존 `--auto`/`-y` 옵션을 사용하세요. 추가 안전 설정은 필요하지 않습니다.

## Auto 모드

Auto는 일상적인 개발에 적합합니다. 일반 도구 권한을 자동 승인하여 클릭을 줄여 주지만, 무제한은 아닙니다.

Auto는 여전히 다음을 존중합니다:

- 명시적 `deny` 규칙.
- 명시적 `ask` 규칙.
- 플랜 모드의 "실행 시작(start execution)" 확인.
- 전역(global), 선호(preference), 피드백, 업데이트, 중복, 민감, 또는 초대형 `remember` 호출과 모든 `forget`에 대한 새로운 인간 승인. 새롭고 범위가 한정된(bounded) 비민감 프로젝트/참조 사실은 생성 전용(create-only)으로 분류되어 프롬프트 없이 저장될 수 있습니다.
- 승인된 플랜의 실행 창 안에서도 중첩 또는 간접 Bash 실행에 대한 인간 승인. Guardian 및 허용(allow) 훅은 이를 대체할 수 없습니다. 매개변수/산술 확장, 할당, 리다이렉트, glob은 Auto의 빠른 경로(fast path)에 그대로 남아 있습니다.
- 유효 정책이 `auto`, `prompt`, 또는 `writes`인 경우의 MCP 파괴적 호출.
- 질문하기(절대 자동 응답되지 않음).

### Auto가 질문하는 경우

Auto는 구성할 또 다른 기능이 아니라 하나의 동작으로 설계되었습니다:

> Auto는 권한 정책이 허용하는 작업을 실행합니다. 새 플랜, 제품 트레이드오프, 또는 그 밖의 진정한 사용자 소유 결정이 나타날 때에만 질문합니다.

- 워크스페이스 읽기/쓰기, 명령, 소스/구성/워크플로 편집, 의존성, 테스트, 외부 작업은 기존 권한 정책을 따릅니다. Auto Guard는 더 이상 위험 기반 프롬프트를 추가하지 않습니다.
- 결과적으로 기본 Auto는 작업이 `git push`, 게시, 배포, 파괴적, 권한 상승, 또는 전역적이라는 이유만으로는 질문하지 않습니다. 명시적 `ask`/`deny`, 샌드박스, MCP, 도구별 권한 경계는 여전히 적용됩니다.
- 초기 일반 작업 플랜 생성은 빠른 경로(fast path)에 유지됩니다. 활성 구조화된 플랜이 재작성되면 독립 검토자가 기존 플랜, 제안된 플랜, 사용자 작업을 비교합니다. 합리적인 구현 개선은 계속됩니다. 진정한 제품, 전략, 또는 범위 선택은 제거된 단계와 추가된 단계를 보여주는 중립적 플랜 결정 카드를 표시합니다. **새 플랜을 채택하고 계속하기(Adopt the new plan and continue)**를 선택하면 진행되고, **채택하지 않고 Auto에 조정 방법 알리기(Do not adopt; tell Auto how to adjust)**를 선택하면 결정을 제출하지 않고 인라인 피드백 필드가 열립니다.
- 실패는 실행 신뢰성 신호이지 작업 전체의 권한 경계가 아닙니다. 관련 없는 작업은 Auto Guard 확인이나 복구 검토 호출 없이 즉시 계속됩니다. 정확히 실패한 작업의 재시도만 범위가 한정된 복구 검토에 들어가며, 진정한 구조화된 플랜 선택만이 인간 결정 카드를 여는 유일한 복구 경로로 남습니다.
- 시간 초과에는 재시도 전에 현재 상태와 부분적 영향을 확인하라는 간결한 실패 경로 안내가 제공됩니다. 사용자에게 Auto를 재설정하거나, 모드를 전환하거나, 세션을 다시 시작하라고 요청하지 않습니다.
- 진단과 복구는 호스트가 소유한 고정 에피소드(Episode) 예산 안에서 자동으로 계속됩니다(설정 없음): 동일한 정확한 작업은 3회 실패 후 중단됩니다. 에피소드는 실제 진전 없이 6회의 실행 실패, 누적 3회의 검토자 거부, 또는 이미 중단된 작업의 3회 재제출이 발생하면 추가 변경/검증을 중단합니다. 매개변수나 명령 변경은 에피소드 합계를 재설정할 수 없습니다. 성공적인 변경과 호스트가 인정한 검증은 무진전 예산을 재설정하지만, 진단용 읽기는 재설정하지 않습니다.
- 에피소드가 하드 중단되면 호스트가 검증한 읽기 전용 진단은 계속 사용 가능한 상태로 유지되며, 추가 변경과 검증은 격리됩니다. 그러면 Auto는 요약 전용(summarize-only) 라운드를 한 번 받고 차분한 `recovery_paused` 상태를 표시합니다(전송 실패가 아님). 다음 사용자 메시지는 자동으로 새 에피소드를 엽니다.
- **다른 접근 방식 시도(Try another approach)**, 플랜의 **실행 시작(Start execution)**, 실제 도구 권한 모드 변경, 새 일반 사용자 메시지는 각각 새 에피소드를 엽니다. Goal 자동 계속과 하위 에이전트(sub-agent)는 현재 에피소드를 상속합니다. 명시적 **작업 계속(Continue task)** 승인은 에피소드 순환을 넘어 TaskScope에 유지됩니다.
- 검토자 부재는 일반 복구를 프롬프트로 바꾸지 않습니다. 감지된 구조화된 플랜 전환은 Auto가 조용히 결정하는 대신 사용자에게 넘겨집니다.
- 헤드리스 실행은 진정한 플랜 결정이 필요할 때 기본 거부(fail closed)로 동작합니다.
- 헤드리스 Ask/Auto/DontAsk도 동일한 `Bash=<literal>`이 명시적으로 허용되지 않으면 중첩 또는 간접 Bash에서 기본 거부로 동작합니다.
- 이러한 경계는 Auto에서만 유효합니다. Ask와 YOLO는 기존 승인 의미론을 유지하며, 별도로 배워야 할 안전 설정은 없습니다.

Auto는 파일시스템 스냅샷이나 롤백 메커니즘이 아닙니다. 변경 사항을 되돌릴 수 있어야 한다면 깨끗한 Git 브랜치나 일회용 워크트리(worktree)를 사용하세요. 시작 여부는 Plan이 결정하고, 이후 일반 실행은 Auto가 처리합니다.

Auto Guard에는 사용자가 관리할 작성자 도구 허용 목록(allowlist)이나 재설정 절차가 없습니다. 작업별 중단은 좁은 범위로 유지되며, 에피소드 하드 중단은 현재 자동 복구 턴만 일시 중지합니다. 권한 정책과 샌드박스가 계속해서 기능 경계를 소유합니다.

## Yolo 모드

Yolo는 연속 실행을 최대화합니다. 일반 도구 권한 프롬프트를 건너뛰므로 쓰기와 명령의 중단이 줄어듭니다.

Yolo는 중첩/간접 Bash 인간 승인 요구 사항을 우회할 수 있는 유일한 승인 자세입니다. 그래도 명시적 `deny` 규칙이나 샌드박스는 우회하지 않습니다.

### 활성화 방법

- 컴포저 아래에서 Yolo를 직접 선택하거나, 새 세션 기본값으로 선택하거나, **설정(Settings) → 단축키(Shortcuts)**에 표시된 현재 바인딩(기본값 `Ctrl+Y`/`Cmd+Y`)을 사용하세요.
- Ask 또는 Auto를 직접 선택하면 Yolo를 벗어납니다.
- 단축키로 진입하면 Patty Code는 이전 Ask/Auto 기준선을 기억하고 다음 토글에서 복원합니다.

## 협업 모드와의 조합

| 조합 | 동작 |
| --- | --- |
| Plan + Ask | 플랜 작성 중에는 게이트된 호출이 대기합니다. 플랜 승인 후에는 일반 작성자 폴백이 자동 허용되지만, 명시적 `ask`/`deny`, MCP `prompt`/`writes`, 강제된 새 승인은 여전히 적용됩니다. |
| Plan + Auto | 플랜 확인은 여전히 필요합니다. 시작 후에는 일반 도구 권한이 자동 승인됩니다. |
| Plan + Yolo | 플랜 확인은 여전히 필요합니다. 시작 후에는 일반 도구 프롬프트가 최소화됩니다. |
| Goal + Ask | Goal은 계속 진행되지만 도구 승인은 여전히 사용자를 위해 일시 중지됩니다. |
| Goal + Auto | 대부분의 일상 Goal 작업에 가장 적합합니다: 명시적 규칙 경계를 갖춘 연속 진행. |
| Goal + Yolo | 매우 명확하고 롤백 가능한 Goal 작업용. 위험도가 가장 높습니다. |

## 권장 기본값

- 신뢰할 수 있는 일상 작업에는 **Auto**를 선호하세요.
- 워크스페이스, 데이터, 또는 작업의 위험이 불분명할 때는 **Ask**를 사용하세요.
- 플랜이 확인되고 트리가 일회용이거나 쉽게 롤백될 수 있을 때만 **Yolo**를 사용하세요.
